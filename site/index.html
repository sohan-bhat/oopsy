    How it works

    1. It hooks in

      oops init adds a small hook to your shell and to your coding agents, so every command and every agent file edit passes Oopsy on its way to run. Turn on oops watch to keep the previous version of files you save in an editor too.

    2. It snapshots first

      When a command is about to destroy files, Oopsy saves them first. It reads the command for what it names, and keeps a mirror of your project for everything else, so make clean, npm run reset and scripts it has never seen are undoable too. Copy on write clones on APFS, Btrfs, XFS and ReFS, and hard links on NTFS and ext4, make that instant and nearly free on disk.

      It reads the command with a real shell parser, so it knows rm, mv, cp, sed -i, dd, find -delete, rsync --delete, redirects, and git reset, clean, checkout, branch -D, stash drop and push --force. On Windows it also reads PowerShell, like Remove-Item -Recurse and Get-ChildItem *.log | Remove-Item, and cmd.exe, like rd /s /q.

    3. You type oops

      oops shows what it will bring back, then restores it. oops list shows the rest, and oops undo <id> brings back any one of them.

      It never overwrites. If a file exists again, the saved copy lands next to it as name.oops-42.ext.

    Postgres, too.

    Run oops db proxy --upstream postgres://... and point your app or agent at the proxy instead. Before any DROP TABLE, TRUNCATE, DELETE or UPDATE reaches the database, Oopsy copies exactly the rows it is about to touch, inside the same transaction, so a rollback discards the snapshot too.

    Or skip the setup: oops db wrap -- npm run dev runs your command with DATABASE_URL pointed at a temporary proxy.

    It also saves view and function definitions before they are dropped, the rows an upsert is about to overwrite, and a compressed pg_dump before DROP DATABASE. For changes made straight in psql or by a migration tool, oops db protect adds triggers that keep them undoable too.

    What it does not catch

    • Other machines. Commands run over ssh change another computer, so undo there needs Oopsy installed there too.
    • A full disk. Oopsy skips a copy that would break its free space floor, 5% of the disk between 2 and 20 GB, and tells you right then. Clones and hard links never need the room.
    • A dead disk. Snapshots live on the same disk as your files unless you point oops config store at a second drive.

    Only partly covered

    • With oops watch off, a program that writes into a file in place on NTFS, or a statically linked one doing so on ext4. Oopsy sees the change but cannot keep the old version there, and says so.
    • A rebuildable folder like node_modules deleted by a program that never names it anywhere Oopsy can read. Rebuild it.
    • Data inside cloud resources and Kubernetes volumes. Oopsy saves the objects, the Terraform state, Docker volumes and Helm releases, not the rows, files or disks inside them.
    • Database changes that skip the proxy, unless you turn on oops db protect. With it on, inserts and ALTER statements are still not reversed.
    • Without Clink, cmd.exe lines that start with a command other than del, rd, move, copy, git, npm, node, python, make and a few more.

    Questions

    Why not just Ctrl+Z?

    Undo lives inside your editor. rm, git and your database never ask your editor first, so once a file is gone from disk there is no history to step back through. In a terminal, Ctrl+Z only suspends the running job.

    Why not git?

    Git protects what you committed. Uncommitted edits, untracked files, .env and everything in .gitignore are exactly what rm -rf and git reset --hard wipe out. Oopsy covers the work between commits.

    Why not Time Machine?

    Time Machine runs about once an hour, to another disk, and getting a folder back means scrolling through a timeline. Oopsy snapshots the exact moment before the command and restores in one word. Keep both.

    Does it catch make clean and my own scripts?

    Yes. Besides reading the command line, Oopsy keeps a mirror of each project you work in, where every file is a copy on write clone or a hard link, so it costs almost no disk. A quick walk before each command keeps it current, and whatever the command changes or deletes moves into its snapshot. Read only commands like ls and git status are skipped at no cost. Folders you can rebuild, like node_modules, are saved whole only when a command or its script names them.

    What about my editor and my agent's edit tool?

    Claude Code, Codex, Cursor and Gemini CLI file edits are saved before they happen, once per version, compressed, so repeats cost nothing; oops undoes the last one. For saves in your editor, run oops watch on: a small background service keeps the previous version of every file you change, and oops list --watch shows them.

    How much disk does it use?

    On APFS, Btrfs, XFS, ReFS and Windows Dev Drives, a snapshot is a copy on write clone. It shares storage with the original and costs almost nothing until the files change. On NTFS and ext4, a command that only deletes is saved with hard links, which cost nothing either. Overwrites there get a real copy, compressed with NTFS compression on Windows and zstd elsewhere, of any size as long as the disk keeps a safe floor free afterwards: 5% of the disk, between 2 and 20 GB. A project mirror costs a few hundred bytes per file. Snapshots are kept for 7 days and capped at 5 GB in total, and you can change both with oops config. To survive a dead disk, oops config store moves everything to a second drive, at the cost of one compressed copy of each project there.

    Does it work on Windows?

    Yes. Install it with Scoop or the PowerShell line above, then run oops init. It hooks PowerShell 7, Windows PowerShell, Git Bash and cmd.exe (every typed line with Clink, the common destructive commands without it), plus Claude Code, Codex CLI, Cursor and Gemini CLI, whichever shell they run commands in. Files another program has locked are skipped with a warning.
